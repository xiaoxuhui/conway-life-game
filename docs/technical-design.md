# 技术设计

## 1. 技术目标与约束

- 使用原生 HTML、CSS 和 JavaScript，不依赖后端。
- 核心玩法在断网状态下可用。
- MVP 不引入框架、打包器或运行时依赖。
- 业务逻辑与界面渲染分离，使规则可以独立测试。
- 默认规模下优先保证清晰和稳定，再考虑极限性能。

## 2. 计划中的目录结构

以下是开发阶段的目标结构，当前不会提前创建空代码文件：

```text
conway-life-game/
├─ index.html               # 页面结构和静态内容
├─ styles/
│  └─ main.css              # 布局、主题、响应式与可访问性样式
├─ scripts/
│  ├─ life-engine.js        # 纯规则、棋盘状态与序列化
│  ├─ renderer.js           # Canvas 绘制和坐标转换
│  ├─ presets.js            # 预设图案数据
│  └─ app.js                # 控件、计时器和用户交互
├─ tests/
│  └─ life-engine.test.js   # 核心规则自动化测试
├─ docs/
├─ README.md
└─ .gitignore
```

## 3. 架构分层

### 规则层 `life-engine.js`

职责：

- 创建、读取和更新棋盘状态。
- 计算单个下一代，不接触 DOM 或计时器。
- 统计活细胞数量。
- 放置预设和校验导入数据。

规则层应尽量由纯函数组成，同一输入始终产生同一输出，方便测试和复现问题。

### 渲染层 `renderer.js`

职责：

- 把棋盘绘制到 Canvas。
- 根据元素尺寸和设备像素比生成清晰画面。
- 把鼠标/触摸坐标转换为行列坐标。
- 不自行改变棋盘数据。

选择 Canvas 而不是为每个格子创建 DOM 元素，原因是中等规模棋盘更新频繁时更稳定，也更容易控制完整棋盘的缩放。控制按钮仍使用语义化 HTML。

### 应用层 `app.js`

职责：

- 保存当前棋盘、代数、速度和运行状态。
- 连接按钮、滑块、键盘和指针事件。
- 管理唯一的演化计时器。
- 在每次状态变化后统一刷新画面和状态文本。

## 4. 状态模型

建议使用一维 `Uint8Array` 保存固定尺寸棋盘：

```text
index = row × columns + column
0 = 死亡
1 = 存活
```

应用状态示意：

```js
{
  rows: 40,
  columns: 60,
  cells: Uint8Array,
  generation: 0,
  running: false,
  stepsPerSecond: 5
}
```

规则计算使用一份新的数组保存下一代，避免同一代内的更新互相污染。棋盘边界之外统一视为死亡。

## 5. 演化算法

MVP 采用完整扫描：

1. 遍历每个格子。
2. 统计合法范围内的 8 个邻居。
3. 根据 B3/S23 写入下一状态数组。
4. 完成后整体替换旧数组，代数加 1。

时间复杂度为 `O(rows × columns)`，60 × 40 的目标规模足够轻量。稀疏集合、分块或 Web Worker 优化仅在真实测量表明需要时引入。

## 6. 运行调度

- 整个应用只允许存在一个计时器句柄。
- “开始”创建调度，“暂停”清除调度并释放句柄。
- 速度变化时安全地重建调度，不立即额外执行一代。
- 标签页进入隐藏状态时自动暂停。
- 不把视觉帧率等同于演化速度；后续若需高速度，再评估基于 `requestAnimationFrame` 的累积时间方案。

## 7. 绘制输入

统一使用 Pointer Events 支持鼠标、触控笔和触摸：

- `pointerdown` 时读取起点状态，确定本次手势是绘制还是擦除。
- `pointermove` 时只把经过格子设置为目标状态，不执行 toggle。
- 使用指针捕获处理移出 Canvas 后的结束事件。
- 运行中忽略棋盘编辑输入。

## 8. 导入/导出格式（P1）

首版自有 JSON 格式：

```json
{
  "format": "conway-life-game",
  "version": 1,
  "rows": 40,
  "columns": 60,
  "generation": 0,
  "alive": [[1, 2], [2, 3], [3, 1], [3, 2], [3, 3]]
}
```

导入时依次校验：文件大小上限、JSON 语法、格式名、版本、尺寸范围、代数以及每个坐标。只有全部通过后才替换当前状态。导出使用坐标列表，便于人类阅读和未来格式迁移。

## 9. 测试策略

### 规则单元测试

- 空棋盘保持为空。
- 单个细胞下一代死亡。
- 2 × 2 方块保持不变。
- 闪烁器周期为 2。
- 滑翔机经过 4 代后平移一个对角格。
- 边界外按死亡处理，且不会越界。
- 输入状态不会被 `nextGeneration` 原地修改。

### 交互测试

- 开始/暂停不会产生重复计时器。
- 单步只增加一代。
- 拖动始终是连续绘制或连续擦除。
- 清空、随机、预设能正确暂停并重置代数。
- 速度标签与实际周期一致。

### 人工验收

- Chrome、Edge、Firefox 各完成一次核心流程。
- 桌面宽度、窄窗口和手机宽度进行视觉检查。
- 仅键盘完成开始、暂停、单步和清空。
- 断网后重新打开仍可使用。

## 10. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 本地 `file://` 对模块或文件操作有限制 | 双击运行失败 | MVP 使用普通脚本；导入用文件选择器；开发后在全新环境实测 |
| Canvas 在高分屏模糊 | 可读性下降 | 按设备像素比设置内部分辨率 |
| 手机格子过小 | 难以绘制 | 限定棋盘规模，提供预设，评审缩放/滚动方案 |
| 计时器重复启动 | 跳代、性能问题 | 单一句柄与状态守卫，并编写交互测试 |
| 导入恶意或巨大文件 | 卡顿或状态损坏 | 大小、结构和坐标范围校验；验证通过后再提交状态 |

## 11. 技术验证结论

- Canvas 会根据实际显示尺寸和设备像素比重建内部像素尺寸；桌面与手机宽度下均保持 3:2 比例、完整显示且非空白。
- Pointer Events 的鼠标点击和拖动已在真实浏览器通过；真实触摸设备手势仍需后续人工补测。
- JSON 导入、非法文件保护和导出反馈已在本地静态服务器环境通过。
- 页面仅使用传统本地脚本和相对资源，不使用 ES Module、网络请求或远程资源。自动化浏览器安全策略禁止 `file://` 导航，因此双击运行保留为人工验收项。
