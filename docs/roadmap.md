# 开发计划与阶段门

## 原则

每一阶段都必须有可检查的产物和退出条件。阶段未通过时，不把后续功能提前混入当前工作，以免界面和代码在需求不稳时快速膨胀。

## 阶段 0：需求与设计（当前阶段）

产物：

- 需求文档。
- 交互与视觉设计。
- 技术设计。
- MVP 验收清单和待确认问题。

退出条件：

- [x] 用户确认 MVP 的 P0 范围。
- [x] 用户确认默认棋盘、速度、随机密度和视觉方向。
- [x] 清空撤销、运行时编辑、手机棋盘策略已有决定。
- [x] 技术探针完成并记录结论。

## 阶段 1：可点击的静态原型

目标：先验证布局和操作顺序，不实现生命规则。

产物：

- 桌面和手机布局。
- 全部 P0 控件及其视觉状态。
- 棋盘占位与状态栏。

退出条件：

- [ ] 首次使用者能指出如何绘制和开始。
- [ ] 主次操作层级清楚。
- [ ] 窄窗口下没有不可达控件或横向滚动。
- [ ] 用户确认视觉方向后再进入功能开发。

## 阶段 2：规则引擎

目标：在不连接界面的前提下实现并证明 B3/S23 正确。

产物：

- 独立规则模块。
- 方块、闪烁器、滑翔机和边界行为测试。

退出条件：

- [ ] 所有规则单元测试通过。
- [ ] 规则模块不依赖 DOM。
- [ ] 输入状态不被意外修改。

## 阶段 3：可用 MVP

目标：连接棋盘、控制与规则，完成所有 P0 需求。

产物：

- 点击和拖动编辑。
- 开始/暂停、单步、清空、随机和速度调节。
- 代数、状态和活细胞数量。
- 本地运行说明。

退出条件：

- [ ] `requirements.md` 的 MVP 验收清单全部通过。
- [ ] 三种桌面浏览器完成核心流程。
- [ ] 至少一次全新环境的本地运行验证。
- [ ] 用户完成一次实际试玩反馈。

## 阶段 4：增强功能

按用户试玩反馈决定顺序：

1. 预设图案。
2. JSON 导入/导出。
3. 键盘快捷键和可能的一步撤销。

每项独立验收，不一次性打包上线。

## 阶段 5：发布准备

- 完善说明、截图和许可证。
- 检查离线运行、性能和可访问性。
- 创建首个版本标签。

## 变更规则

- 新需求先记录到需求文档，标明优先级和验收条件。
- 改变边界模型、渲染方式或数据格式时，先更新技术设计。
- 改变主流程或控件位置时，先更新交互设计。
- 只有当前阶段的退出条件全部满足，才进入下一阶段。
